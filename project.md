# Проект: Bronegovorka - v1.0.0

## 1. Паспорт проекта

**Участники:** Мирный Игорь Дмитриевич, Варфоломеева Анастасия Андреевна.

**Продукт:** REST API бронирования переговорных для небольшой учебной или рабочей команды.

**Планируемый выпуск:** v1.0.0 - локально запускаемый сервис с аутентификацией, просмотром комнат, созданием и отменой бронирований, проверками прав и конфликтов интервалов.

**Исходное состояние:** на момент заполнения подготовлена проектная документация, исходный код отсутствует. После создания MVP команда зафиксирует commit и тег.

**Репозиторий:** https://github.com/switerElly/bronegovorka.

### Контекст и пользователи

Продукт разрабатывают два студента. Обычный пользователь просматривает комнаты и занятые интервалы, создает и отменяет собственные брони. Администратор управляет комнатами и может отменять любую бронь. В расписании обычному пользователю видны комната и интервал, но не чужие учетные данные. Решение о выпуске принимают оба участника на основании результатов проверок.

Основной сценарий: пользователь входит, выбирает комнату и свободный интервал, создает бронь и при необходимости отменяет ее. Пересекающиеся активные брони одной комнаты запрещены.

### Границы

**В проект входит:**

- Один API на Python с FastAPI, SQLite и SQLAlchemy; демонстрация через встроенную OpenAPI/Swagger-документацию.
- Учетные записи с ролями `user` и `admin`, создаваемые локальной командой настройки; публичная регистрация отсутствует.
- Вход по паролю и выдача непрозрачного случайного токена с ограниченным сроком действия. Пароли хранятся как Argon2id-хеши, токены - в виде хешей. Выход отзывает текущий токен.
- Просмотр комнат; создание и редактирование комнаты администратором.
- Создание брони, просмотр расписания и собственных броней, отмена брони владельцем или администратором.
- Валидация времени и идентификаторов, ограничение выдачи списков, журналирование существенных событий, воспроизводимые проверки и инструкция запуска.

**За пределами проекта:** отдельный frontend, календарные интеграции, почта, SSO, повторяющиеся брони, платежи, несколько организаций, распределенная база данных и публичное размещение в интернете.

### Компоненты, взаимодействия и границы доверия

Клиент Swagger/HTTP → FastAPI → слой правил доступа и бронирования → SQLite.

Недоверенные запросы проходят аутентификацию и проверку структуры. Идентификатор владельца берется из серверной сессии; клиент не может назначить себе другого владельца или роль администратора. Права проверяются при каждой операции над объектом. Файл БД и конфигурация доступны только оператору приложения. Репозиторий и среда CI образуют отдельную границу: реальные пароли и рабочие токены туда не попадают.

## 4. Целевой Secure SDLC

1. **Требования:** оба участника согласуют сценарии, роли и инварианты. Артефакты - этот документ и контракт OpenAPI.
2. **Проектирование:** Варфоломеева А.А. предлагает схему доступа; Мирный И.Д. - правила времени и конкурентных записей. Каждый проверяет решение партнера.
3. **Реализация:** небольшие PR с проверкой партнером. Используются ORM/параметризованные запросы, готовое хеширование паролей и серверная проверка прав.
4. **Исходная проверка:** фиксируются commit, версии, команды и результаты методов из раздела 5. Срабатывания разбираются вручную.
5. **Улучшение:** выбирается подтвержденный риск или разрыв, выполняется изменение и повторяется соответствующая проверка.
6. **Выпуск:** оба участника проверяют инструкцию с чистой БД, полноту свидетельств и остаточные риски; затем создают тег v1.0.0.

Контрольные точки: согласование паспорта; фиксация baseline; разбор исходных результатов; приемка улучшения; совместное решение о выпуске. Для каждого выпуска обязательны проверка доступа, инвариантов бронирования и зависимостей. Дополнительные методы включаются при появлении новых рисков.

Блокируют выпуск подтвержденная отмена чужой брони, повышение роли, двойное бронирование и применимая критичная проблема зависимости. Исключение оформляется с причиной, ограничением эксплуатации, ответственным и сроком пересмотра; оба участника согласуют принятие риска.

## 5. Технологический профиль

Версии инструментов будут закреплены в файле зависимостей при создании каркаса и сохранены вместе с результатами. Указанные команды - план будущего запуска, сейчас соответствующие файлы отсутствуют.

### Метод 1: проверка авторизации API

**Риск:** доступ к чужим бронированиям и административным операциям.

**Цель и область:** проверить матрицу `anonymous/user/admin`, владельца объекта, просроченный и отозванный токен для всех защищенных операций.

**Этап:** исходная проверка, проверка изменений и допуск к выпуску.

**Инструменты:** pytest и HTTPX; плановая команда `python -m pytest tests/test_access.py -v`.

**Ведущий:** Мирный И.Д. **Проверка партнером:** Варфоломеева А.А. повторяет сценарии с чистой БД и проверяет полноту матрицы.

**Свидетельства:** тесты, матрица прав, вывод проверки без токенов и паролей в `evidence/access/`.

**Ограничения:** тесты проверяют заданные сценарии, а не доказывают отсутствие всех ошибок аутентификации.

### Метод 2: бизнес-правила и конкурентное бронирование

**Риск:** пересекающиеся брони, ошибочные границы интервалов и гонки записи.

**Цель и область:** проверить интервалы `[start, end)`: `start < end`, время с часовым поясом и нормализация в UTC, запрет прошедшего начала, разрешение соседних интервалов. Отмененная бронь освобождает интервал. Из нескольких одновременных запросов на один интервал успешен ровно один.

**Этап:** проектирование механизма записи, исходная и повторная проверка.

**Инструменты:** pytest, HTTPX и отдельный тест реального процесса API с файловой SQLite и независимыми соединениями. Плановые команды: `python -m pytest tests/test_booking.py -v` и `python -m pytest tests/test_concurrency.py -v`.

**Ведущий:** Варфоломеева А.А. **Проверка партнером:** Мирный И.Д. повторяет конкурентный сценарий и проверяет состояние БД.

**Свидетельства:** сценарии, параметры параллелизма, ответы и состояние БД в `evidence/booking/`.

**Ограничения:** нагрузочный тест не является доказательством атомарности. Нужна также проверка транзакционного решения: блокировка записи должна охватывать проверку пересечения и вставку; отдельные операции «проверить, затем вставить» недостаточны. Масштабирование на несколько серверов не проверяется.

### Метод 3: анализ кода и зависимостей

**Риск:** опасные конструкции Python и известные применимые проблемы зависимостей.

**Инструменты и область:** Bandit для `app/`, pip-audit для закрепленных зависимостей; плановые команды `python -m bandit -r app -f json` и `python -m pip_audit -r requirements.txt -f json`.

**Ведущий:** Мирный И.Д. настраивает анализ кода, Варфоломеева А.А. - анализ зависимостей; каждый проверяет результаты партнера.

**Свидетельства:** команды, версии, исходный вывод и разобранные существенные находки в `evidence/static/` и `evidence/dependencies/`.

**Ограничения:** ложные срабатывания возможны; отсутствие находок не подтверждает правильность прав или бизнес-логики. База известных проблем изменяется, поэтому фиксируется дата проверки.

## 8. Улучшение и повторная проверка

**Статус: улучшение не выполнено.** Предварительный кандидат - автоматизация проверки конкурентного бронирования и ее запуск в CI. Это помогает выявлять регрессии при изменении транзакций. Если исходная проверка выявит более существенную проблему, выбор будет пересмотрен.

**План повторной проверки:** один и тот же набор сценариев на baseline и измененном commit; сравнение результатов и проверка партнером. Намеренное создание уязвимости не предусматривается. Если каркас уже корректен, полезным улучшением может стать проверка, сборка или воспроизводимость.

**Ссылка на изменение и результат до/после:** появятся после выполнения.

**План вклада:** Мирный И.Д. ведет сценарии конкуренции и инженерное изменение; Варфоломеева А.А. воспроизводит проверку, проверяет PR и настраивает запуск в CI. Фактический вклад будет отражен по истории изменений.

## 9. Решение о выпуске

**Текущее решение: отложить выпуск v1.0.0.** Сервис еще не реализован; свидетельств проверки нет. Публикация проектного документа не означает выпуск продукта.

Для допуска требуются запускаемый сервис, воспроизводимые проверки, подтвержденное улучшение, разобранные существенные находки и отсутствие блокирующих проблем. Финальное решение принимает команда и подкрепляет ссылками на свидетельства.

**Предварительные ограничения и остаточные риски:** SQLite ограничивает параллелизм; производительность и публичное размещение не исследуются; оператор локальной машины имеет доступ к БД; защита от перебора паролей не входит в минимальную демонстрационную версию. Разрешенная среда v1.0.0 - локальный запуск на синтетических данных. Для сетевой эксплуатации потребуются отдельная оценка, TLS, ограничение запросов и управление секретами.

## 11. Управленческая записка

Команда планирует подготовить v1.0.0 небольшого API бронирования переговорных. Объем ограничен одним сервисом, двумя ролями и базовыми операциями с комнатами и бронями; интерфейс демонстрации - Swagger. Главные защищаемые свойства - корректность расписания и невозможность изменить чужую бронь.

Выбраны проверки авторизации, правил времени, конкурентных записей, кода и зависимостей. Каждый участник ведет содержательную часть, а партнер воспроизводит результат. Полезное улучшение будет выбрано по результатам исходной проверки; предварительный вариант - автоматизация конкурентного сценария в CI.

На дату документа готов только план. Проверки не выполнены, улучшение не подтверждено, выпуск отложен. После реализации команда зафиксирует baseline и соберет свидетельства для решения. Первый выпуск предназначен для локальной демонстрации на синтетических данных. Сетевое использование потребует дополнительных мер и отдельного решения.
